Caso: el usuario no encuentra una plantilla para su estructura de evento

Mini resumen de este circuito:
Usuario entra al wizard
Se crea solicitud en D
Usuario arma todo

Backend:
Crea estructura real

RESUMEN
Diferencia Sin Plantilla vs Con Plantilla
Con Plantilla	Sin Plantilla
Backend crea tramos/accesos desde plantilla	Front crea todo en memoria
Usuario solo edita	Usuario construye desde cero
No se agregan tramos	Se agregan libremente
No se modifican relaciones	Se construyen manualmente

El wizard no llama al backend hasta el final.
Todo se arma en memoria.
El backend recibe todo junto.

¿Qué pasa si el usuario cierra la pantalla?
Hoy:
Se crea solicitud D al iniciar wizard
Se guarda el wizard en localStorage
No se llamó todavía al backend de estructura
Entonces:
La solicitud queda en estado D
No hay tramos creados
No hay accesos creados
No hay nada aplicado al evento
Solo existe un registro D vacío o semi vacío.

¿El usuario puede retomar el wizard?
Actualmente: NO (para no complicar esta fase)
A futuro podría (si así lo decidimos)

Cómo se guardan en el front (sin complicar)
Opción recomendada (para MVP)
?? Guardado en memoria + persistencia en localStorage
Así si el usuario:
vuelve para atrás
refresca la página
cierra y vuelve
no pierde todo.
Estructura en el front (un solo objeto)
El front maneja un objeto tipo:
wizard = {
  fecha_base,
  lugar_base,
  direccion_base,
  latitud_base,
  longitud_base,
  tramos: [],
  accesos: [],
  relaciones: []
}
Cada vez que agrega un tramo:
lo pushea al array tramos
lo guarda en state
(opcional) lo serializa en localStorage
Lo mismo con accesos.

¿Cómo permite “ir y volver” en el wizard?
Porque los steps leen del mismo estado.
Step 1 (Tramos)
Muestra wizard.tramos
Botón “Agregar tramo” abre modal/form
Al guardar:
wizard.tramos = [...wizard.tramos, nuevoTramo]
Step 2 (Accesos)
Muestra wizard.accesos
Agregar acceso ? push al array
Step 3 (Relaciones)
Dibuja la matriz en base a:
wizard.tramos
wizard.accesos
Y los checks salen de wizard.relaciones
Si vuelve para atrás:
nada se pierde porque todo sigue en el estado.

¿Y cómo se maneja “orden”?
En el front lo más simple es:
El orden se calcula automáticamente:
orden = tramos.length + 1
orden = accesos.length + 1
Si borra o reordena, recalculás.

Recomendación práctica (para evitar dolores)
? Guardar el wizard en localStorage con clave por evento:
eventia:wizardEstructura:{idEvento}
Ejemplo:
eventia:wizardEstructura:10
Entonces:
si el usuario sale sin guardar, cuando vuelve recuperás estado
cuando guardó todo OK, borrás esa clave

¿Cuándo se manda al backend?
Solo al final:
? Botón: Guardar estructura
Hace:
POST /eventos_plantillas/CrearEstructuraManual?idEvento=10
Body = wizard completo.

Validaciones por step (para que no se rompa)
Step tramos
debe haber al menos 1 tramo para pasar al step accesos
Step accesos
debe haber al menos 1 acceso
debe existir 1 acceso default
Step relaciones
cada acceso debe tener al menos 1 relación
(opcional) warning si hay tramos sin uso o accesos vacíos

Te dejo el “contrato” completo para que el front lo implemente sin pensar: estructura del state, actions tipo Redux (aunque usen Zustand/Context/Redux da igual), validaciones por step y el payload final que se manda al backend.

1) State único del wizard (por evento)
Clave en localStorage:
eventia:wizardEstructura:{idEvento}
Estructura (TypeScript-friendly):
type WizardEstructuraState = {
  idEvento: number;

  // base común (para no pedir ubicación/fecha en cada tramo)
  fecha_base: string;        // ISO DateTimeOffset
  lugar_base: string;
  direccion_base: string;
  latitud_base?: number | null;
  longitud_base?: number | null;

  registrar_solicitud: boolean;   // default true
  motivo: "NO_ENCONTRO_PLANTILLA" | "NINGUNA_ME_SIRVIO";
  detalle?: string | null;
  id_plantilla_referida?: number | null;

  tramos: TramoDraft[];
  accesos: AccesoDraft[];
  relaciones: RelacionDraft[]; // par acceso_orden + tramo_orden

  // control UX
  step: 1 | 2 | 3;
  last_saved_at?: string | null;
};

type TramoDraft = {
  orden: number;                 // 1..n
  id_tramo_tipo?: number | null; // smallint
  nombre: string;
  leyenda_visible?: string | null;
  activo: boolean;               // default true
};

type AccesoDraft = {
  orden: number;                 // 1..n
  nombre: string;
  mensaje_rsvp?: string | null;
  es_default: boolean;           // exactamente 1 true
  activo: boolean;               // default true
};

type RelacionDraft = {
  acceso_orden: number;
  tramo_orden: number;
};
?? Nota: todo se guarda en memoria del front + localStorage.
El backend se llama solo al final.

2) Actions (Redux-style)
Estas acciones cubren el 100% del wizard (agregar/editar/borrar, reordenar, relacionar).
Wizard base
INIT_WIZARD_FROM_EVENT(idEvento, defaults)
LOAD_WIZARD_FROM_STORAGE(idEvento)
RESET_WIZARD(idEvento) (borra state + storage)
SET_STEP(step)
SET_BASE_FIELDS({ fecha_base, lugar_base, direccion_base, latitud_base, longitud_base })
SET_SOLICITUD_META({ motivo, detalle, id_plantilla_referida, registrar_solicitud })
Tramos
ADD_TRAMO(tramoSinOrden) ? asigna orden = tramos.length + 1
UPDATE_TRAMO(orden, patch)
DELETE_TRAMO(orden) ? reordenar 1..n y limpiar relaciones que apunten al tramo eliminado
REORDER_TRAMOS(fromOrden, toOrden) ? recalcula orden + actualiza relaciones
Accesos
ADD_ACCESO(accesoSinOrden) ? asigna orden = accesos.length + 1
UPDATE_ACCESO(orden, patch)
DELETE_ACCESO(orden) ? reordenar 1..n y limpiar relaciones que apunten al acceso eliminado
REORDER_ACCESOS(fromOrden, toOrden)
SET_DEFAULT_ACCESO(orden) ? pone ese es_default=true y el resto false
Relaciones (matriz)
TOGGLE_RELACION(acceso_orden, tramo_orden, checked)
si checked=true ? agrega si no existe
si checked=false ? elimina si existe
SET_ACCESO_INCLUYE_TODOS(acceso_orden, checked)
checked=true ? crea relaciones con todos los tramos
checked=false ? elimina todas las relaciones de ese acceso
CLEAR_RELACIONES() (si querés reset)
Persistencia
PERSIST_TO_STORAGE() (se llama en cada action o con debounce)
MARK_SAVED(timestamp) (cuando vuelve OK del backend)

3) Validaciones por step (bloquean “Siguiente”)
Step 1 — Tramos
? Reglas:
tramos.length >= 1
cada tramo:
nombre requerido (1..80)
leyenda_visible opcional (<=200)
id_tramo_tipo opcional (pero recomendado)
Step 2 — Accesos
? Reglas:
accesos.length >= 1
exactamente 1 acceso con es_default=true
cada acceso:
nombre requerido (1..80)
mensaje opcional
Step 3 — Relaciones
? Reglas:
para cada acceso activo: debe tener al menos 1 relación
toda relación debe apuntar a un orden existente de acceso y tramo
Warnings (no bloqueantes):
hay tramos sin ningún acceso
hay accesos con pocos tramos (raro pero permitido)
